How a Ticket Works

What happens from the moment someone clicks the panel to the moment their ticket closes.

Opening a Ticket

A member picks a category from the panel's dropdown. Before the modal opens, the bot checks, in order:

  • Is ticket creation currently enabled?
  • Is the user individually blacklisted?
  • Does the user hold a server-wide Ticket Blacklist Role?
  • Does the user hold a role blacklisted from this specific category?
  • Does the user already have another ticket open, in any category?
  • Is the user on cooldown from a recently closed ticket?

If every check passes, a modal collects timezone, display name, and whether they can join a private server. The channel is then created and auto-named using that category's prefix and running number — e.g. fallen-carry-0001.

Closing a Ticket

There are three ways to close a ticket:

  • Close button in the channel — asks for confirmation first
  • /close [reason] — staff closes immediately, reason is logged in the transcript
  • /requestclose — asks the ticket opener to confirm; staff cannot force this through, only the opener can approve or decline

On close: a transcript is generated, the opener is DMed the link, the action is logged, an 8-hour cooldown is applied, and the channel is deleted shortly after.

If a ticket channel is deleted directly in Discord instead of through one of the methods above, the bot detects the deletion and cleans up its internal record automatically — so the user isn't permanently blocked from opening a new ticket.

Carry Team Application

At /dashboard/carry-applications, carry managers can pause responses and set the denial cooldown from 0 to 365 days (14 by default). Cooldown changes apply to existing denials from their decision time. Applicants see pending, accepted, denied with a live countdown, or closed status at the application portal.

Select accepted applications to remove their acceptance and allow reapplication while retaining staff history. Select denied applications to clear their cooldown. Cleared cooldowns remain cleared after policy changes; closing responses still prevents new submissions. Review roles and Bot/Webhook delivery remain in Access Control.

Ticket Categories

The dropdown options members see when opening a ticket, configured in Carry Manager Settings.

  • Label, description, emoji — what shows in the dropdown
  • Blacklist Roles — members with these roles can't select this specific category
  • Name Prefix — tickets auto-name as prefix-0001, prefix-0002, and so on

Ticket Messages

Two editable messages, both in Carry Manager Settings, sent automatically when a ticket is created.

"Ticket Created" Redirect Message

Sent privately to the member the moment they submit the ticket form — only they can see it. Plain text, one field.

Ticket-Channel Welcome Message

Posted inside the new ticket channel itself, right after it's created. Configurable:

  • Format — Embed (styled box) or Plain text
  • Message Content — text sent alongside/outside the embed, usually the opener's mention
  • Embed Title, Description, Color, Footer — only used in Embed format
  • Show Timezone / Show Display Name / Show "Can Join?" — Yes/No toggles for whether each of the opener's ticket-form answers appears as a field

Placeholders

Available in both messages — any left unused are simply not replaced:

{category}The ticket category label they chose

Access Control

Admin-only settings for dashboard access, role permissions, ticket blacklists and logging.

  • Allowed users and roles control access to the dashboard.
  • Page permissions govern Analytics, Carry Manager Settings and Transcripts.
  • Ticket viewer and blacklist roles control ticket visibility and opening restrictions.
  • Staff command permissions determine which users and roles may use available command groups.
  • Logging channels control ticket, blacklist and warning records.
  • Configured Bot Admin IDs are read-only and provided through ADMIN_USER_IDS on the host.

April Fools Ad Gag

The draft dashboard places the Ad Gag editor in Carry Manager Settings. Admins can configure image/video-style joke advertisements, countdown (1–120 seconds), shuffle settings, sponsors, headlines and links. The legacy /admin address redirects to the integrated editor.

Downtime & Offline Schedule

Learn how scheduled offline hours work, where to configure them, and how to check the public bot status.

What downtime means

The offline schedule defines periods when the Discord bot should be offline. The website and public status pages can remain accessible during those periods. A scheduled offline window is different from an unexpected outage or an API rate limit.

Configure your offline schedule

  • Open Dashboard → Access Control with an authorized administrator account.
  • Expand the 🕒 Bot Offline Schedule accordion. It starts collapsed by default.
  • Enable the schedule, then set a valid timezone (for example, America/New_York).
  • For each day, add one or more enabled Start and End times. Windows can cross midnight.
  • Click Save Offline Schedule and check the Status page to confirm the configuration appears.
Changing the offline schedule requires administrator access. Other visitors can view its public status and configured time windows without access to your dashboard.

Understanding the status labels

  • Active: The bot is connected and currently available.
  • Inactive / Scheduled offline: The bot is offline or inside a scheduled offline window.
  • API Limited: Discord API restrictions are temporarily affecting connectivity; this is not a planned downtime window.
  • Disabled time window: The saved entry remains visible but does not activate downtime.

Use the configured schedule timezone when reading the time windows; it may differ from your own browser timezone. Updates to the public page may require a refresh after the schedule is saved.

Staff Commands

Slash Command Reference

Ticket management commands are visible in Discord's slash-command picker, but can only be executed by authorized staff with Manage Channels, configured bot-admin access, or explicit Basic Command Access. Commands tied to a ticket require an active ticket channel.

/close [reason]
Closes the current ticket immediately. Reason is optional and gets logged in the transcript.
/request-close [reason]
Staff send a Components V2 close-approval panel to the ticket opener, with Approve and Decline buttons. Only the opener can respond.
This is blocked while the ticket is in progress. The existing /requestclose command remains available as an alias.
/start-ticket
Staff mark the ticket as in progress, preventing the opener from closing it via the channel's Close Ticket button, a pending close approval, or other owner-initiated close routes.
The lock persists in the active ticket record; authorized staff may still close the ticket.
/end-ticket
Staff finish the in-progress state and restore the ticket opener's ability to close it.
Old close-approval prompts become invalid after a lock transition; send a fresh /request-close prompt if needed.
/rename <name>
Renames the current ticket channel.
/add <user>
Grants a member view + chat access to the current ticket channel.
Fails harmlessly if the user already has access, and can't be used to add a bot.
/remove <user>
Revokes a member's channel-specific access to the current ticket, added earlier via /add.
/ticketnumber <number>
Adjusts the shared ticket numbering that is used across categories.
The next ticket uses the updated shared counter; confirm the resulting number before changing a live sequence.
/move <category>
Moves the ticket to a different configured category — renames it with that category's prefix/counter, and physically relocates the channel if a Discord Category ID is set.
Autocompletes from your configured Ticket Categories.
/scan_url <url>
Checks a URL against VirusTotal and returns the scan result.

Data & Persistence

The bot supports MongoDB for ticket records, settings, transcripts, access control and logs. Some legacy features still use local files.

MongoDB

Configure MONGODB_URI on the host. Check the logs to confirm a working connection; an environment variable alone does not guarantee one.

Local files and fallback

Individual ticket blacklist entries are currently stored in local JSON. Other functions may use data/*.json or local HTML transcript files when MongoDB is unavailable. Ephemeral hosting can lose local data on redeploy.

Back up MongoDB and any local-only data before changing hosting. Some features do not automatically synchronize local files with MongoDB.

Dashboard speed

The draft page refactor fetches data only for the selected section, reuses settings during one HTTP request, and retrieves transcripts in batches. These optimizations have not yet been benchmarked on the live service.
